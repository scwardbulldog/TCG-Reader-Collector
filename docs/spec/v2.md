# v2 spec: a hardened Catalog and card model

**Status: draft.** The Catalog, card model and migration decisions are settled. The UX and scanning sections are provisional until the phone walkthrough ([#54](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/54)) and the English-name ticket ([#56](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/56)) land; they are marked as such and will be reshaped, not just extended.

Hand-off spec for a build effort. It evolves [v1.md](v1.md) and does not restate it: a section here replaces the matching v1 section where it says so, and everything else in v1 (plus the post-v1 tickets already shipped) stays as built. The linked tickets remain the record of the reasoning. Vocabulary is in [GLOSSARY.md](../../GLOSSARY.md); v2 adds **Card**, **Treatment**, **Rarity**, **Product code** and **No longer in the Catalog**.

Decision records: [ADR 0004](../adr/0004-v2-card-model-derived-card-bandai-authoritative.md) (the v2 model), [ADR 0002](../adr/0002-printing-key-game-language-bandai-id.md) (Printing key, with its v2 note). ADR 0001 and 0003 are unchanged. The Catalog file format is in [catalog-format.md](../catalog-format.md), section "Planned for v2".

Source: [wayfinder map #51](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/51).

## 1. Overview & goals

v1 tracks one flat list of **Printings**. That works until the collector wants to see the same **Card** across its **Variants** and **Languages**: v1 can only link them by hand-comparing **Base Numbers**, parses the Variant from a Bandai ID suffix, and carries almost no per-Printing facts (no **Treatment**, no **Product code**).

v2 goals:

1. A **Card** concept that links every **Variant** and **Language** by **Base Number**, with names in both **Languages** available to the collector.
2. A richer, more trustworthy **Catalog** file: Variant, **Rarity**, **Product code** and **Treatment** published by the pipeline instead of guessed in the app.
3. A simpler store: one **Printing** table, and refresh/restore rules that never lose an **Owned Copy**.
4. The UX and scanning hardening found in the walkthrough (provisional, sections 7 and 8).

Still one **Game**, two **Languages**, single user, sideloaded Pixel APK, phone-only storage. No v1 dataset or backup is *required* to survive, but v1 backups and the v1 database do (section 5), because the Printing key is unchanged and it costs little.

**Standing constraint:** no over-engineered solutions. Design for the sources and scenarios actually found (Bandai, collector-recorded, a curated overlay), not hypothetical ones.

**Acceptance criteria**

- Every section below can be built without a further design decision, except those explicitly marked provisional or open (section 9).

## 2. Card model

Replaces v1 section 4's "Variant derived from the ID suffix" and the `known_printing` table. Source: [#55](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/55), [ADR 0004](../adr/0004-v2-card-model-derived-card-bandai-authoritative.md).

- **Card is derived.** A **Card** is the set of **Printings** sharing a **Game** and **Base Number**, across **Languages** and **Variants**. It has no table, file or id of its own; it exists wherever at least one **Printing** does, including a **Custom Printing**. A two-level Card + Printing file stays an option only if a card-level fact appears that no Printing carries.
- **Printing key unchanged:** Game + Language + opaque source ID (including derived `@packId` IDs and `custom:<uuid>`). **Owned Copy** points at a **Printing**, never a **Card**.
- **One Printing table.** `known_printing` merges into the Catalog Printing table. A row's origin is Catalog or Custom. The **No longer in the Catalog** flag replaces the old second table.
- **A Custom Printing is never merged** into a later Catalog Printing, even for the same card. (A "convert to Catalog Printing" action is a possible v3 feature.)
- **Bandai is authoritative.** The pipeline publishes **Variant**, **Rarity** (Bandai's code) and an optional **Product code**; where another source disagrees, Bandai wins.
- **Card name per Language** is read from that Language's **Printings** (Normal preferred). A name is never a key. A JP-only card, or one never listed in a Language, shows the name it has; no machine translation (v3).

**Acceptance criteria**

- The domain module can list all **Printings** of a **Card** (Game + Base Number), grouped by **Language** and then **Variant**, from the Printing table alone.
- No code derives **Variant** by parsing the Bandai ID; it reads the published field. A Custom Printing has no Variant (as today); filters on Variant exclude it.
- A **Card**'s name in a **Language** is the Normal Printing's name in that Language, else any Printing's name in it; absent, no name is shown for that Language.
- An **Owned Copy** has no reference to a **Card**; the CSV and backup carry only the Printing reference.

## 3. Catalog file and pipeline

Replaces v1 section 3's file shape. Format detail lives in [catalog-format.md](../catalog-format.md) "Planned for v2"; this section is the requirement. Source: [#58](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/58), [#57](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/57).

**File.** One file per **Language** at the existing path, `schemaVersion` 2, no Card-level file. Existing fields stay (`id`, `baseNumber`, `name`, `imageUrl`, `releaseProduct`, `rarity`) and it gains `variant` (`normal` / `alternate-art` / `reprint`), optional `productCode`, optional `treatments` (absence means unknown). No `productId`. `rarity` stays Bandai's code; Japanese `SPカード` is normalised to `SP CARD`, any other unknown code is passed through with a build warning. The `?NNNNNN` image cache-buster is stripped. Optional fields never bump the version; changing a field's meaning does.

**Treatment overlay.** A hand-edited file in the private `TCG-Catalog` repo, keyed by Language + Printing ID, with a closed tag vocabulary (Parallel, Manga, SP, Wanted Poster, foil kinds, Stamped and similar). An unknown tag fails the build; an entry that matches no Printing only warns and publishes nothing. It never creates, removes or re-keys a Printing. English booster sets are covered first; everything else stays untagged (unknown). The app never calls a third party, and no third-party code or API runs in the pipeline.

**Pipeline defects, fixed in the `vegapull` fork and re-pinned** (not worked around in the pipeline), each with a fixture and test:

- The "Remarks" block drops `info_obtained`.
- A Bandai typo makes the pipeline skip JP `P-160`.

**Publish gate.** Existing refusals unchanged (empty, unreadable previous, more than 10% drop, more than half of promos missing "Information Obtained"). Added: a warning for an unknown rarity code, a failure for an unknown Treatment tag.

**Licensing.** Bandai's terms allow personal use only, so card data, the overlay and the published files stay in the private repo and the public repo never holds them. Third-party sources were rejected for the Catalog itself because none has both clear terms and structured variant data ([#57](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/57)); the overlay is hand-curated, not copied from one. This is context, not legal advice.

**Acceptance criteria**

- The pipeline publishes `schemaVersion` 2 files with `variant` on every Printing and `rarity` normalised as above; `productCode` appears only where Bandai's title has a bracket code.
- Published image URLs have no query string.
- A fixture run with the Remarks block restored shows `info_obtained` retained, and one with the `P-160` typo shows the JP card present.
- An overlay with an unknown tag fails the build; one with an unmatched entry passes with a warning and the published file is unchanged by it.
- The gate additions above exist, and the existing gate tests still pass.
- The public repo and APK still contain no Catalog or overlay data.

## 4. Data model, storage and migration

Replaces v1 section 7's storage paragraph and the table layout of section 4. Source: [#59](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/59), [ADR 0004](../adr/0004-v2-card-model-derived-card-bandai-authoritative.md).

- **One Printing table** with the Catalog fields above (including `variant`, `rarity`, `productCode`, `treatments`), an origin (Catalog or Custom) and the **No longer in the Catalog** flag, plus last-known details for flagged rows. Custom rows hold the collector's own details.
- **Catalog and Collection stay separate in effect:** a Catalog refresh never changes an **Owned Copy**, **Location** or backup status.
- **Room migration 4 → 5, in place.** Keep `owned_copy`, `location` and `backup_status`. Build the Printing table from `known_printing`: custom rows stay Custom, the rest are flagged until the first v2 refresh clears them. Drop `catalog_printing` and `catalog_version` so the next launch downloads the v2 files. No data is lost; a failed migration must not leave a half-migrated database.
- **App reader.** The Catalog reader accepts `schemaVersion` 2 (and, as today, rejects anything else, keeping the last good Catalog). The v2 app does not need to read version 1 files.

**Acceptance criteria**

- A database at version 4 with Owned Copies, Locations, known and custom Printings migrates to 5 with every **Owned Copy** and **Location** unchanged and every Printing row present (known ones flagged, custom ones Custom). A migration test covers it.
- After migration and the first v2 download, previously flagged rows that the file lists are unflagged and take the new details.
- There is no `known_printing` table and no `rememberPrintings` code left.
- A `schemaVersion` 1 or unknown-version file is rejected and the stored Catalog is untouched.

## 5. Refresh, backup and restore

Replaces v1 section 4 "Printings that vanish", section 6 "Catalog gaps" and section 7's backup content rule where stated. Source: [#59](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/59).

**Refresh.** For each **Language** a refresh replaces Catalog rows from the new file: details update, an unchanged ID keeps its row. A Catalog row the file drops is kept and flagged **No longer in the Catalog** if any **Owned Copy** uses it, and deleted if none does. A flagged row the file lists again clears its flag and takes the new details. **Custom** rows are never touched. The `beforeReplace` hook in `CatalogUpdater` goes away because flagged rows simply stay.

**Re-ID'd cards.** Never remapped. The old ID stays on the **Owned Copy**, flagged; the new ID is a separate Printing. No `replacedBy` hint in the file. (Moving a copy by hand is section 7's "Change Printing".)

**Backup.** Still a manual, versioned JSON file, Collection only. It now also carries last-known details for rows flagged **No longer in the Catalog**, alongside the Custom Printings it already carries. Printings the Catalog still has need nothing. Whether this is an optional field or a `schemaVersion` bump is settled in the build; v1 backups must still restore.

**Restore.** Validation, confirmation, atomic replace and the reminders are unchanged. On restore the Catalog's details win when it has the Printing; otherwise the backup's last-known details make it a flagged row. An **Unresolved Printing** (identifier only) now arises only from older backups. This reopens v1's "backups never hold Catalog details" rule, only for rows the Catalog cannot supply.

**Acceptance criteria**

- A refresh that drops a used Printing keeps it flagged with its last-known details and the copy attached; a dropped unused Printing is deleted; a returning flagged Printing is unflagged; Custom Printings and all **Owned Copies** are unchanged. (Tests on the domain refresh logic.)
- A re-ID'd card leaves the old Owned Copy on the old, flagged Printing and adds the new Printing separately.
- A backup taken with a flagged row, restored on a fresh install with a Catalog that lacks it, shows the row flagged with its last-known name, not a bare identifier.
- The same backup restored where the Catalog has the Printing shows the Catalog's details and no flag.
- A v1 backup still restores, with unknown Printings shown as **Unresolved Printing**.

## 6. Names, search and the Card view

Provisional in presentation; the domain behaviour below is firm. Source: [map #51](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/51) notes, [#55](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/55); presentation to be settled by [#56](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/56) and [#54](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/54).

Firm:

- The collector can see a **Card**'s name in both **Languages** wherever the app has it, linked by **Base Number**. JP-only cards show the Japanese name only.
- Search by name matches a **Card**'s name in either **Language**. It stays limited to the session's **Language** for **Printings** in a **Scan Session** unless widened (as v1 manual search is).
- The **Card**-level view lists every **Printing** of a **Card**, grouped by **Language** and **Variant**, with **Rarity**, **Treatment** (when known) and **Release Product** (with **Product code** when present) on each Printing.
- Treatment absent means unknown; never present it as "plain".

Provisional until #54 and #56: where the second name shows (confirmation, Collection row, detail), how it sits beside the first, and whether the **Collection** list becomes Card-first or keeps v1's one-row-per-**Printing** with a Card detail screen. Default if nothing better emerges: keep v1's list and add a Card detail reachable from a Printing.

**Acceptance criteria**

- Searching an English name and a Japanese name for the same **Card** finds the same **Card**'s Printings (subject to the Language scope).
- A **Card** with only a JP Printing shows the Japanese name and no English name or placeholder translation.
- The Card view lists Printings of one **Card** across EN and JP and across Variants, and shows **Treatment** only where published.

## 7. UX changes (provisional)

To be reshaped by the walkthrough ([#54](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/54)); this section only collects what is already known.

Already specified and continuing on their own tickets (post-v1 overrides of v1 section 5 that remain in force):

- [#44](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/44): a "None of these" action on every Printing proposal, leading to the Custom Printing flow.
- [#48](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/48): hint the EN/JP switch from Japanese script on the locked frame (the Language still changes only by the collector).
- [#49](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/49): Bulk Add review shows each row's photo thumbnails.
- [#46](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/46): scanner debug capture.
- Shipped post-v1 and now baseline: Custom Printing (#43), Bulk Add (#34 to #37), Scan Session without setup with a switchable EN/JP and Location at add time (#47), promo product naming and per-product Printings (#41, #50).

New in v2:

- **Change an Owned Copy's Printing.** Nothing today lets the collector move a copy to another **Printing** of any origin (fixes scan mistakes, rescues copies on flagged Printings, and makes a later "convert to Catalog Printing" cheap). Required, whatever shape #54 gives it. Rules: the target is any **Printing**; the copy keeps its condition, **Location** and notes; it is a single edit, not a remap of other copies.
- **Display the new Catalog facts.** **Rarity**, **Treatment** and **Product code** appear where Printings are listed or compared (confirmation, detail, filters). Filters and sort by **Product code** are allowed ("used for sorting and grouping, never identity"). Exact layout is for #54.
- **UX findings from #54** graduate into tickets or the map's fog; none are specified here yet.

**Acceptance criteria**

- An **Owned Copy** can be moved to another **Printing** (including from a flagged one) with condition, **Location** and notes unchanged; other copies of either Printing are untouched.
- **Rarity** and, where known, **Treatment** and **Product code** are visible on the Printing views named above.

## 9. Out of scope, open items and risks

**Out of scope for v2**

- Machine translation of JP-only card names (v3).
- "Convert to Catalog Printing" (v3).
- Third-party data in the Catalog, the app or the pipeline's runtime. Never-listed promos are covered by **Custom Printings** and the Treatment overlay, not by ingesting another source ([#45](https://github.com/scwardbulldog/TCG-Reader-Collector/issues/45) is answered by this decision and can close when this spec is approved).
- Other Games, iPhone, Play Store, hosted backend, pricing, graded slabs, Chinese Printings: unchanged from v1 section 9.
- Treatment coverage beyond English booster sets.

**Open items**

- Provisional presentation in sections 6 to 8 (#54, #56).
- Backup change: optional field or `schemaVersion` bump (decided in the build, section 5).
- Whether Bandai's pack IDs (behind derived `@packId` IDs) stay stable over time; unverified. If they change, those Printings are re-ID'd and the flag rules above apply.
- Whether TCGplayer-derived labels may be republished; not needed unless the overlay is later sourced from them. Hand-curation avoids the question.

**Risks**

- **Overlay upkeep.** Treatments are hand-maintained; coverage lags new sets. Unknown is a valid state, so a gap is invisible rather than wrong.
- **Stale cached image.** Stripping the cache-buster means a Bandai image swapped at the same URL stays stale in the app cache until evicted. Accepted.
- **Rollout order.** Publish the `schemaVersion` 2 files first (a v1 app build then rejects them and keeps its old Catalog), then install the v2 app. There must be no period with both formats published.
- **Pipeline dependence** on `vegapull` and Bandai's markup is unchanged from v1.

**Acceptance criteria**

- None of the out-of-scope items is built in v2.
